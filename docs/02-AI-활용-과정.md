## 4. 검증 방법

1. 자동 테스트. 28개(20:39)에서 31, 38, 39, 58, 86, 112개(22:51)로 늘었고, 서버 수리 뒤 152개, HWP 표 처리 뒤 179개입니다. 유료 AI는 부르지 않고 판정 규칙, 파일 처리, 한도, 가짜 공급자 응답을 검사합니다. 지금 공개 주소의 배포본은 112개 기준입니다.
2. 라이브 측정. 배포마다 실제 호출로 확인했습니다. 21:16 GPT-5.4 PDF 65.4초·인용 78개 일치, 22:27 Opus PDF 40.2초·인용 61개, 22:45~22:50 실제 5쪽 공고 분석 42.9초·인용 66/66과 판정 3사례(전부 충족, 미충족, 대부분 빈 답), 01:47 실제 공고 분석 40.1초·판정 9.4초. 모바일은 WebKit iPhone 13 에뮬레이션까지 했고 실제 아이폰은 아닙니다.
3. 인용 감사. 저장된 분석 25회의 인용 1,136개를 앱과 다른 PDF 추출기로 다시 대조했습니다. 1,134개는 지정한 쪽에 그대로 있었고, 2개는 가운뎃점 표기만 달랐고, 원문에 없는 인용은 0개였습니다. 다만 25회 중 22회는 직접 만든 합성 공고이고, HWPX 10회는 앱이 추출한 글로 대조해 독립 검증이 아닙니다.
4. 블라인드 평가. 평가자가 자기 점수(71점)를 먼저 적어 둔 뒤, 이전 점수를 모르는 에이전트 3명이 README와 화면, 문서만으로 채점했습니다. 63점이 나왔고 교차 확인 뒤 65점(기획 16/25, AI 과정 16/25)으로 정했습니다. 코드 안에만 있는 기획과 과정은 점수가 되지 않았습니다. 이 문서를 쓰는 이유입니다.
5. 모델 비교 설계. 2차 비교는 비교 도중 코드가 바뀌지 않게 동결한 스냅샷으로 돌렸고, 프롬프트와 스키마의 해시를 기록했습니다. 판정 비교는 같은 분석 결과와 같은 기준 시각을 넣어 분석 단계의 흔들림을 뺐습니다. 한계도 분명합니다. 모든 비교가 설정별 1회이고, 정답 체크 3개는 모든 설정이 통과해 모델을 가르지 못했습니다.
6. 독립 검토. 서버 수리로 바뀐 39개 파일을 Codex가 01:34~01:52에 검토했습니다. 서명 토큰을 거친 실제 판정 경로에서 틀린 '가능'을 재현했고, 필수 조건 삭제를 정답으로 고정한 테스트도 찾았습니다. 검토자는 자기 환경 제약 때문에 테스트 전체 통과를 다시 확인하지는 못했습니다.

## 5. 비용과 운영 선택

- 단가. 운영 모델 Opus 5.5 fast는 보고서 기재 단가로 입력 100만 토큰당 8달러, 출력 40달러입니다. 실제 5쪽 공고로 분석 1회와 판정 2회를 하면 약 1.2달러로 추정했습니다. 토큰 수로 계산한 값이며 청구서가 아닙니다[^4]. fast는 standard의 두 배 단가이고, fast를 고른 이유는 기록이 없습니다[확인 필요: 질문 6].
- 비교 비용. 1차 비교에서 Astra high fast의 PDF 1건 추정 비용은 1.546달러로 GPT-5.4(0.084달러)의 약 18배였습니다. 비용과 지연을 함께 잰 것은 이 비교뿐입니다.
- 한도 해제. 22:48에 호출 한도를 환경변수로 켤 때만 작동하게 바꾸고, 운영에서는 켜지 않았습니다. README에 적은 이유는 "기존 Redis 사용량이 소진되어 있어도 심사를 막지 않고, 같은 Wi-Fi의 심사위원들이 사용 횟수를 나눠 쓰지 않습니다"입니다. 한도를 켜면 IP별 10분당 분석 8회가 코드에 고정돼 있어 같은 와이파이의 심사위원이 함께 막힐 수 있습니다.
- 위험. 공개 주소의 누구나 유료 호출을 반복할 수 있습니다. 앱이 막는 것은 같은 세션의 동시 실행뿐입니다. 운영본의 출력 상한은 128,000토큰이고(32,000·16,000으로 낮춘 수정은 미배포), 200쪽 문서를 가정한 보고서 추정으로 1회 최악 9~10달러입니다. 공급자 계정의 지출 상한은 확인하지 못했습니다[확인 필요: 질문 9].

## 6. 실패에서 배운 것

1. 인용이 맞아도 해석은 틀립니다. GPT-5.4는 인용 73개가 모두 원문과 맞았는데 병역 나이 연장을 우대 조건으로 분류했습니다. HWPX 분석은 인용 8개가 모두 맞았는데 원문에 없는 "신청일 기준"을 썼습니다. 인용 대조는 필요조건일 뿐이라서, 날짜를 원문 날짜·요일과 맞춰 보는 검사를 따로 넣었습니다(미배포).
2. 검증이 결과 전체를 버리면 사용자는 실패만 봅니다. 모델이 조건 10개 중 1개를 빠뜨리거나 검색 제안을 한 조건에 2개 넣으면 서버가 판정 전체를 502로 버렸습니다. 실제 공고 판정 9회 중 3회가 여기서 실패했습니다. 앱의 원칙대로라면 빠진 조건은 '확인 필요'로 채우면 됩니다. 그렇게 고치고 1회 재시도를 넣었습니다(미배포).
3. 테스트 통과와 자기 평가는 정확성의 증거가 아닙니다. 서버 수리는 테스트 152개를 통과했지만, 새 나이 계산이 거주 미충족을 덮어 '가능'으로 바꿨고, 형식 수선이 근거가 빈 필수 조건을 지웠습니다. 다른 도구의 검토가 이를 잡았고 배포를 멈췄습니다. 점수에서도 같은 일이 있었습니다. Codex가 자기 산출물을 평가한 점수는 약 76점, 블라인드 패널은 63점이었습니다.

## 7. 남은 과제

- 차단 결함 5건 재수리. 검토의 재현 사례를 회귀 테스트로 넣고, 통과하면 서버 수리분을 배포합니다.
- 실제 공고 정답셋. 5~10건에 사람이 조건·마감일·서류 정답을 달고, 조건 재현율과 정밀도, 마감일 정확도, 틀린 '충족' 수를 잽니다. 같은 입력을 반복해 분산도 잽니다.
- 사용자 관찰. 대상 사용자가 같은 공고를 앱 없이, 앱으로 읽을 때 시간과 정답률을 비교합니다[확인 필요: 질문 10].
- 운영. 심사 뒤 호출 한도 다시 켜기, 계정 지출 상한, 개발 중 대화창에 붙여 넣은 API 키 재발급[확인 필요: 질문 9].
- 미해결 결함. 새로고침하면 결과가 사라지는 문제, 배포 사이 판정 409, 인용과 설명의 의미 대조, HWP 병합 표. 자세한 목록은 03-오류-유형표.md에 있습니다.
